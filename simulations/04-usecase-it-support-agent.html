📊 NL-to-SQL Database Execution (Lesson 08)

Witness how natural language queries are parsed, secure SELECT query validations run, and SQLite results compile inside ReAct.

Step 1: Schema Introspection

Understanding the Catalog Schema

The database agent is supplied a clean description of columns during tool definition so the model knows which attributes to target in its query.

Table: products
Columns:
  - id: INTEGER (Primary Key)
  - name: TEXT (Product Name)
  - category: TEXT (Category e.g. Furniture, Electronics)
  - price: REAL (Retail Price in USD)
  - stock: INTEGER (Available inventory)
Step 2: SQL Query Generation

Translating Natural Language to SQL

An executive asks: "Which furniture items cost more than $200?". Sridhar's agent graph translates this into a valid SQLite query.

# Generated SQL string passed as argument to tool
SELECT name, price, stock 
FROM products 
WHERE category = 'Furniture' AND price > 200
Step 3: Security Validation Guard

Enforcing read-only SELECT security guidelines

Before executing the query against `mission2_products.sqlite`, the custom tool runs a security parser, filtering out mutation keywords like `DROP`, `DELETE`, or `UPDATE` to secure inventory metrics.

# Security Guard Logic
forbidden_keywords = ["insert", "update", "delete", "drop", "create", "alter"]
# Checks and successfully validates query is SELECT-only!
Step 4: Output Compilation

Visual Results Formatting

The rows returned by SQLite are formatted inside the ReAct messages list, and compiled into a clean Markdown table.

| Product Name | Price | Stock |
|---|---|---|
| Ergonomic Desk Chair | $249.99 | 45 |
| Bamboo Standing Desk | $599.00 | 15 |

🛡️ Takeaway for Enterprise Agents

Direct relational database access offers immense speed, but must always be guarded. Exposing raw SQL executes dangerous operations if not validated by secure, read-only SELECT filters inside the custom tool definition.
