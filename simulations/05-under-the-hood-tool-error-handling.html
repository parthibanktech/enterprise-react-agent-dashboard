🛡️ Resilient Self-Correction & Error Recovery (Lesson 10)

Witness how a ReAct loop handles runtime exceptions and column typos to dynamically rewrite plans without failing.

ReAct Cycle 1: The Misstep

Attempting SQL Query with Typos

The user asks: "What is the category and pric of Ergonomic Desk Chair?". The model makes a column name misspelling.

🧠 THINK (Thought)

"The user wants category and price. I will write a SQL SELECT query targeting 'category' and 'pric'."

🎬 ACT (Action)

Call `query_products_database` with query: "SELECT category, pric FROM products WHERE name = 'Ergonomic Desk Chair'"

👁️ OBSERVE (Error Observation)

The SQLite tool returns: "Database SQLite Error: no such column: pric".

ReAct Cycle 2: Self-Reflection & Correction

Reading error logs to recover on the fly

Instead of throwing a python runtime exception, the error message is loaded back into short-term memory as a descriptive observation.

🧠 THINK (Thought)

"The database returned 'no such column: pric'. I made a typo. Checking schema... yes, the correct column is named 'price'. I will rewrite the query."

🎬 ACT (Action)

Call `query_products_database` with query: "SELECT category, price FROM products WHERE name = 'Ergonomic Desk Chair'"

👁️ OBSERVE (Success Observation)

SQLite executes successfully, returning row: [{"category": "Furniture", "price": 249.99}]

ReAct Cycle 3

Clean Final Summary

# Final conversational response
"The category of the 'Ergonomic Desk Chair' is Furniture, and its price is $249.99."

💡 Resiliency Takeaway

Traditional program routers fail on syntax mistakes. In ReAct, errors are caught, parsed as conversational string parameters, and fed to the LLM to reflect, rewrite arguments, and correct its own execution paths dynamically.
